# Architecture

MiliconfigOS runs as a single Cloudflare Worker that serves three distinct responsibilities.
They share a deployment but never share trust assumptions.

```text
                        ┌──────────────────────────────────────────┐
  browser ──HTTPS──────▶│  control plane                           │
                        │  /            login gateway (homepage)    │
                        │  /admin       workspace UI                │
                        │  /api/v1/*    authenticated JSON API      │
                        │  /s/:token    subscription delivery       │
                        └───────────────┬──────────────────────────┘
                                        │ D1 binding
                        ┌───────────────▼──────────────────────────┐
                        │  Cloudflare D1                           │
                        │  users · endpoints · configurations      │
                        │  subscriptions · usage_daily · audit     │
                        └──────────────────────────────────────────┘
                        ┌──────────────────────────────────────────┐
  proxy client ─WSS────▶│  data plane (same Worker)                │
                        │  VLESS / Trojan / Shadowsocks / xHTTP     │
                        │  byte counters → usage_daily             │
                        └──────────────────────────────────────────┘
```

A configuration link generated by the control plane points at the data plane, but the two
capabilities are verified separately: generation, endpoint reachability, protocol validation and
measured traffic are different results and the UI never collapses them into one status.

## Request flow (`src/index.js`)

1. `ensureD1Schema` / `ensureV4Schema` — idempotent DDL. If a D1 binding exists the Worker never
   silently falls back to memory; a missing binding is reported to the UI and login is refused
   unless `MILI_ALLOW_MEMORY=1` is explicitly set for development.
2. `/api/v1/*` → `src/api/v1.js` (own auth, same-origin checks, JSON errors).
3. WebSocket upgrade → `src/core/runtime.js` (proxy data plane).
4. Legacy API paths (`/:adminPath/api/...`) → `src/api/handlers.js`, kept for existing integrations.
5. `POST` on other paths → xHTTP transport handler.
6. `GET` → homepage proxy (`/__homepage`), login gateway, subscription (`/s/:token`, `/sub/:token`,
   `/:token/sub`), status page, admin workspace.

The admin workspace path defaults to `/admin` (configurable through the `d` setting) and the
first-run setup also returns a generated UUID path; both authorize the same session check, so path
obscurity is never the access control.

## Control-plane modules

| Module | Responsibility |
| --- | --- |
| `config/defaults.js` | 31 base-engine settings, brand, `MAX_USERS_LIMIT = 5`, protocol defaults, legacy informational nodes (retained as data, no longer injected into subscriptions). |
| `config/catalog.js` | Verified DNS providers (addresses + DoH/DoT), DNS modes, TLS fingerprint catalog, ECH entries, protocol/transport/format capability data, catalog version. |
| `config/schema.js` | Central settings schema: types, options, defaults, ranges, sanitisation, `detectConflicts()` for incompatible combinations. |
| `core/engine.js` | `validateCandidate()` (protocol/transport/TLS/DNS/ECH/chain/format rules), `scoreCandidate()` (policy weights + measured health/latency), `buildPlans()` (dedupe, reject with reasons), `configurationRow()` (persisted run record). |
| `core/scanner.js` | Graded probes: syntax → DNS → TCP → TLS → HTTP, plus ECH record inspection. Bounded concurrency, per-check timeouts, explicit `performed` flags. |
| `core/health.js` | Score from the highest successful level, labels, `mapLimit`, DoH answer parsing. |
| `core/security.js` | PBKDF2-SHA256 (210k), constant-time compare, password policy, session cookies, same-origin CSRF check, AES-GCM secret encryption, random tokens. |
| `core/automation.js` | Job runner shared by `POST /api/v1/automation/:id/run` and the Cron Trigger `scheduled()`. |
| `db/d1.js` | Binding detection (`DB`, `D1`, `miliconfig`, …), user CRUD with atomic five-user limit, global settings, audit logs, memory fallback. |
| `db/v4.js` | Sessions, login attempts, endpoint catalog + health history, configurations, subscriptions, usage, automation, Cloudflare token/resources. |
| `subscription/generator.js` | Builds per-user node lists from user settings **and** the persistent endpoint catalog; applies naming (`1+miliconfig`…), per-user node cap, rotation. |
| `subscription/converters.js` | Real serializers: sing-box JSON, Clash/Mihomo YAML, Surge, Loon, Quantumult X, URI list. Each has its own tests. |
| `ui/*` | Server-rendered HTML shells + client script: no framework, no build step, RTL/LTR, three themes. |

## Subscription pipeline

```text
user row (uuid, quota, expiry, config_json)
        │
        ├── enabled endpoint rows (host, port, protocol, country, name)
        │
        ▼
generateUserNodesList()
        │  vless / trojan / ss / xhttp link builders
        │  custom preferred IPs, static Cloudflare addresses, chains
        ▼
finalizeMiliSubscriptionLinks()  → per-user cap + `N+miliconfig` names
        ▼
format serializer (singbox | clash | uri | surge | loon | quanx)
        ▼
/s/:token?target=… with subscription headers (quota, expiry, title)
```

- Tokens are 32 random bytes, stored per user, rotatable and revocable.
- Fetching a subscription increments a download counter only; it never increments traffic.
- Subscription responses are `no-store` and never contain the administrator password, session
  data or the Cloudflare token.

## Configuration engine

`buildPlans()` enumerates protocol × endpoint × client format, then:

1. rejects invalid candidates (unknown/disabled protocol, transport mismatch, invalid host/port,
   disabled IP family, ECH without TLS/DoH/config, chain loop, format that cannot represent the
   protocol);
2. scores the rest from optimization policy (`balanced`, `latency`, `stability`), measured health
   score and latency, and user scope;
3. attaches machine-readable reasons (`code`, `en`, `fa`);
4. stores valid plans in `configurations` with score, issues and reasons.

Rejections are returned as counts plus the first ten details, so "no valid combination" always has
an explanation instead of a silent empty subscription.

## Data model (D1)

| Table | Purpose |
| --- | --- |
| `users` | One row per user slot; `uuid` unique; quota, expiry, node scope, per-user config JSON. |
| `system_config` | Global settings, admin password hash, admin path. |
| `admin_sessions` | SHA-256 hash of session token, expiry, revocation flag, IP. |
| `login_attempts` | Failed/successful login attempts for rate limiting. |
| `endpoints` | Persistent catalog: host, port, family, kind, country, provider, protocol, transport, TLS mode, health score, latency, failures. |
| `endpoint_health` | Per-check history (`level`, `ok`, `latency_ms`, `detail`). |
| `configurations` | Generated plans with validation JSON, reasons and score. |
| `subscriptions` | Per-user token, formats, revocation, download counter. |
| `usage_daily` | Measured bytes per user/day/source. |
| `automation_jobs` / `automation_runs` | Job definitions, schedule state and execution history. |
| `cloudflare_resources` | Resources observed through the Cloudflare API. |
| `audit_logs` | Administrative activity with client IP. |
| `schema_meta` | Schema version marker. |

Migrations: `migrations/0001_init_miliconfig.sql` (v3 tables), `migrations/0002_v4_control_plane.sql`
(v4 tables). `schema.sql` is the complete current schema. All statements are `IF NOT EXISTS`, so
applying them to an existing database preserves data.

## Usage accounting

Bytes are counted while the Worker pipes a proxied stream and written to `usage_daily` with
`source = 'worker-stream'`, then folded into `users.used_bytes`. Panel HTML/API responses are not
counted. Subscription fetches are a separate counter. If the runtime cannot measure something, the
UI prints "not available" rather than an estimate.

## Automation

Jobs are stored in D1 and can be enabled/disabled. `scheduled()` runs due jobs on the configured
cron (every 15 minutes in `wrangler.toml`); the API can also run one immediately. Jobs only report
(detect expiry, quota exhaustion, invalid configurations, refresh endpoint health) and record
history — they never delete users or rewrite subscriptions automatically.

## Local harness vs production

`scripts/dev-server.js` runs the real Worker `fetch` handler on Node with a SQLite adapter behind
the D1 interface, so migrations, sessions, CRUD, generation and serializers are exercised exactly
as in production. Only the `cloudflare:sockets` data plane is unavailable locally; scanner TCP
checks then report the honest error instead of a fake success.
